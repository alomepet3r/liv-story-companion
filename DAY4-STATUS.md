## Day 5, evening — Screen-sleep fix: session wake lock + interruption truthfulness (Oct 30, 2026)

**Founder observation (his phone test, verbatim):** "My screen went to sleep on safari and the recording was interrupted while I was still talking. Can that be fixed?" Two-part fix shipped in `web/app.js`:

**Fix 1 — Screen Wake Lock, SESSION-scoped (founder refinement, same evening).** The founder widened the scope before the build finished: the interaction with Liv is continuous, so the lock is not per-recording. As built:
- **Acquired at the Begin transition** past consent; its home is every post-consent screen (conversation + chapter). Recording start merely ensures it is held (`noteWakeInteraction`). The consent screen itself never holds it — acquisition is gated on `consented`.
- **Idle release:** after **30 minutes** with no interaction the lock is released and the device sleeps naturally. The window is a named constant, **`WAKE_IDLE_MS`** (`30 * 60 * 1000`), so the founder can move it. "Interaction" = pointer/key activity (document-level listeners), a message sent (`send()`), recording start/stop. Each interaction re-arms the idle clock; the first interaction after an idle release re-acquires, and the sitting continues.
- **Re-acquire on return:** `visibilitychange` → visible counts as interaction (idle clock re-armed) and re-requests the lock the browser dropped when the page hid.
- **Full release:** end-session wipe (back on consent) and `pagehide`.
- **Enhancement only, like Pause:** feature-detected (`"wakeLock" in navigator`), every request wrapped so a rejection/failure is swallowed and can never break or block recording or the sitting; a request still in flight when the sitting ends hands the lock straight back. Where unsupported, nothing is faked — the Fix 2 hint stands in (below).

**Fix 2 — Interruption truthfulness (the safety net).** Every audio stop now carries a cause, held in per-take flags reset at recording start: **user Stop** (`stopInitiated`, set by both Stop controls — the deck's Stop and the panel's record button), **Discard/kills** (`discardNext`, shipped this morning), and **unexpected** (the stop event fires with neither — the OS/browser killed the recorder). `visibilitychange` → hidden mid-telling marks the take `interrupted`. In the stop handler: `cutShort = R.interrupted || !R.stopInitiated` (discards still send nothing, checked first).
- A cut take follows the **normal send path** — the partial telling is preserved, per the founder's doctrine that a recording is a telling, not an absolute record — but `sendVoiceTake` announces the truth for that send: **"The screen slept and cut that short — what you said up to then went to Liv."** A normal deliberate stop keeps the usual heard-you line; it never sees the cut copy.
- **State-mismatch resync:** on return to visible, if the recorder is dead while the mic chrome still shows a recording (its stop event never landed), the UI resyncs the way `closePanels` does (`micUiReset`) with the status line "The screen slept, and the recording stopped." If the stop event was merely queued, its send still runs and the cut-short line speaks last.
- **Unsupported-browser hint:** where `navigator.wakeLock` does not exist, the first recording of a session appends one line to the voice status — keeping the screen awake helps, because if the screen sleeps, the recording stops. Once per session (re-armed by the end-session wipe); never shown where the lock is active.

**Honest limits (recorded, not hidden):** the wake lock cannot cover everything. A **manual lock** (the founder pressing the side button), an **app switch** that gets the page discarded, or an **older iOS without the Wake Lock API** (Safari before 16.4) can still cut a recording — no web page can prevent those. What those cases now preserve is the partial take: it still sends, and it is labelled as cut short rather than dressed as a full telling.
